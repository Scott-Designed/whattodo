The empty case is the one that decides the design. Only 30 of 682 published listings can show events today, so most pages look like this one — which means the page cannot lean on the events section to justify itself. It leans on the description, the facts and the neighbours instead, and simply drops the heading it cannot fill. That is the opposite of type.html, which draws all seven kind buckets even when empty — right for a monitoring view you scan, wrong for a page a reader lands on.

The decisions worth arguing with

Four calls, and why

The id is in the URL Not /bells-beach. 45 slugs collide across 221 published rows — toddler-time alone is 32 of them, one per library branch. And kind can change (Go Ride A Wave went venue → shop in a day), so /venue/… would break. a2 is the key keyOf() already uses for saved listings, so it is one key shape across the site, and a wrong slug can redirect to the right one.

Happenings get no page An event page is wrong the day after, all 221 colliding slugs live there, and /noticeboard already lists them. This is for the ~620 rows that persist: venues, spots, shops, makers, groups.

No new fields Every value on both plates is a column the open row already prints. The page earns its place through the URL, the events and the neighbours — not by asking anyone to write more prose for 620 rows.

It needs a link preview api/subject.mjs already serves per-subject titles and descriptions for towns and types. This is the same trick with a third case — and it is the whole point of having an address, since a link with no card is a link nobody presses.

What would still be thin. 117 published happenings carry no types at all — 97 from the library feed — so they reach no type page and would give a venue page a poorer “more like this” tail than it deserves. And 98 places hold 401 published events with no listing row at all, so those events have a room and the room has no page. Both are data passes, not design.
