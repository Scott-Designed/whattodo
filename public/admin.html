What runs by itself

Everything scheduled, plus the things that only run when you ask. The two scrapers are steps in one GitHub Action, so they share a schedule and either can fail without stopping the other.

Where the events come from

Every source anything is ever read from, and what happens when we try. The registry is the Places table, not a list in the code: a place with an events_url gets read, and a place with only a website gets its usual gig paths tried. Adding a source means filling in that cell — never editing a script.

How the runs went

Straight off GitHub's public API — no token, because the repo is public. Press a run to read what the scrapers actually printed; that output is committed into the repo by the run itself, since a job summary on github.com is somewhere nobody looks.

Events

Things that happen on a date and then are over. A date is what separates these from everything else — so what matters here is when, where, and how well the date is actually known. Recurring ones are still events; the How often filter holds the list down to the genuine one-offs.

Activities

The evergreen half — places and things that are simply there, with no date on them. What matters here is whether each one can be found: a real coordinate, a driving distance, and a link that points at a place rather than a search for one.

Places

The venues both of the above hang off — a curated, geocoded row per building. Linking an event to one of these is what gives it a pin, a suburb and a line on the map. Filling in a place’s events_url is also the entire registry for the venue scraper: it reads any row that has one.
